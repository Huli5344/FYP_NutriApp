# Nutri App — Diary and Recommendations (Android)

The Flutter client for the diary and recommendations module. Works with no
network at all; syncs to the Flask backend when it can reach one.

**This folder holds the Dart source only.** The `android/` platform folder is
generated by Flutter rather than checked in, so step 2 below is required before
the first build.

---

## Building the APK

### 1. Install the toolchain

- [Flutter SDK](https://docs.flutter.dev/get-started/install/windows)
- [Android Studio](https://developer.android.com/studio), which brings the
  Android SDK and the emulator

Then check everything is wired up:

```bash
flutter doctor
flutter doctor --android-licenses    # accept with y
```

### 2. Generate the platform folders

From inside this folder:

```bash
flutter create .
flutter pub get
```

`flutter create .` adds `android/`, `ios/` and the other platform directories
around the existing `lib/`. It will not overwrite the Dart source.

### 3. Allow network access

Open `android/app/src/main/AndroidManifest.xml` and add this line inside
`<manifest>`, above `<application>`:

```xml
<uses-permission android:name="android.permission.INTERNET"/>
```

Flutter adds this automatically for debug builds but **not for release**, so a
release APK silently fails every sync without it. The app still runs; it just
never reaches the server.

### 4. Build

```bash
flutter build apk --release
```

The file lands at:

```
build/app/outputs/flutter-apk/app-release.apk
```

Copy it to a phone and open it. Android warns about installing from an unknown
source, which is expected.

For the Play Store internal testing track, build an app bundle instead:

```bash
flutter build appbundle --release
```

## Running during development

```bash
flutter devices          # confirm an emulator or phone is visible
flutter run              # installs and launches, with hot reload
```

Press `r` in the terminal to hot reload after a change, `R` for a full restart.

### Pointing at the backend

`lib/api.dart` holds one constant:

```dart
static const String baseUrl = 'http://10.0.2.2:5000';
```

| Running on | Use |
|---|---|
| Android emulator | `http://10.0.2.2:5000` — the address Android maps to your computer |
| Physical phone | `http://<your computer's LAN IP>:5000`, e.g. `http://192.168.1.24:5000` |
| Hosted backend | the deployed URL |

Inside the emulator, `127.0.0.1` means the emulator itself, which is why the
special address exists.

Start the Flask backend with `python app.py` in the backend folder. It already
listens on all interfaces, so no change is needed there.

## How it is put together

| File | Holds |
|---|---|
| `lib/logic.dart` | Every business rule, as pure functions. No Flutter, no database |
| `lib/models.dart` | Plain data classes |
| `lib/db.dart` | On-device SQLite. The source of truth for the interface |
| `lib/api.dart` | Backend client: sync and recommendations. Every call may fail |
| `lib/seed_data.dart` | Foods and fallback recipes, generated from the backend |
| `lib/ui.dart` | Theme and the shared widgets |
| `lib/screens/` | One file per screen |

`logic.dart` is a direct port of the backend's `logic.py`. It lives on the
device because the diary has to work offline, so the calculations cannot sit
behind an API call.

### The seven screens

| Screen | File |
|---|---|
| Home dashboard | `screens/home_screen.dart` |
| Add food and serving | `screens/add_food_screen.dart` |
| Edit or delete an entry | `screens/edit_entry_screen.dart` |
| Today's diary | `screens/diary_screen.dart` |
| Recommendations | `screens/discover_screen.dart` |
| Recommendation detail | `screens/recipe_detail_screen.dart` |
| Saved to diary | `screens/saved_screen.dart` |

Insights and Profile appear in the tab bar because the design has five
destinations, but they belong to the other two modules and are inert here.

## Offline behaviour

The device's own SQLite database is the source. Screens read and write
locally and never wait on the network. Sync runs on launch and on returning to
the foreground, and a failure is silent: being offline is the normal case for a
food diary, not an error worth interrupting someone over.

Entry ids are UUIDs generated on the device, deletions are tombstones rather
than removals, and conflicts resolve last-write-wins on `updated_at` — the same
rules the server applies. The full contract is in the backend's `SYNC.md`.

### Testing it properly

Install the release APK on a real phone, turn on aeroplane mode, then log three
meals, edit one and delete one. Reconnect and confirm all four changes reach the
server and the deleted one stays deleted. That is the scenario the sync design
exists for, and the one an emulator will not show you.

## Known points

- **Rounding differs from the backend by one calorie on exact halves.** Dart
  rounds half away from zero (910.5 → 911); Python uses banker's rounding
  (910.5 → 910). Harmless, but the two disagree on `607 × 1.5`.
- Recipe suggestions need the backend. With no connection the app falls back to
  25 meals shipped in the binary, and says so on screen.
- The profile is fixed (`Profile` in `lib/models.dart`). Accounts and goals
  belong to another module.
- If your Flutter version rejects `value:` on `DropdownButtonFormField`, change
  those three occurrences to `initialValue:` — the parameter was renamed in a
  recent release.
